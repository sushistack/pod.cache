# 061. 📌 AWS ELB Sticky Session: 흔들림 없는 사용자 경험을 위한 세션 유지 전략

AWS Elastic Load Balancer의 Sticky Session은 클라이언트 요청을 특정 백엔드 인스턴스로 고정하여 사용자 세션 데이터를 유지합니다.
이를 통해 로그인 정보 등 중요한 데이터를 안전하게 관리하며 일관된 사용자 경험을 제공할 수 있습니다.
쿠키 기반으로 동작하며, 로드 밸런서의 부하 분산 균형에 영향을 줄 수 있으므로 신중한 적용이 필요합니다.

---

## 서론: 분산 환경에서의 사용자 세션 관리 문제

현대의 웹 애플리케이션은 높은 가용성과 확장성을 위해 여러 개의 백엔드 서버(예: EC2 인스턴스)에 트래픽을 분산시키는 로드 밸런싱 아키텍처를 흔히 사용합니다. AWS Elastic Load Balancer(ELB)는 이러한 환경에서 핵심적인 역할을 수행하며, 들어오는 요청을 여러 EC2 인스턴스에 효율적으로 배분합니다.

하지만 분산 환경에서는 하나의 사용자가 여러 번 요청을 보낼 때, 각 요청이 다른 백엔드 인스턴스로 라우팅될 수 있습니다. 이로 인해 로그인 정보, 장바구니 내용 등 세션 기반의 데이터가 특정 인스턴스에만 저장되어 있다면, 사용자는 세션이 끊기거나 데이터가 손실되는 문제를 겪을 수 있습니다. 이러한 문제를 해결하기 위해 등장한 개념이 바로 'Sticky Session' 또는 'Session Affinity'입니다.

## 본론: Sticky Session의 이해와 활용

### Sticky Session이란 무엇인가요?

Sticky Session은 로드 밸런서가 특정 클라이언트의 모든 요청을 동일한 백엔드 인스턴스로 지속적으로 라우팅하도록 하는 기능입니다. 일반적인 로드 밸런싱은 요청을 여러 인스턴스에 고르게 분산하는 것을 목표로 하지만, Sticky Session은 특정 클라이언트의 세션 '고정성'을 우선시합니다.

예를 들어, 클라이언트 A가 처음 로드 밸런서에 요청을 보냈고, 이 요청이 EC2 인스턴스 1로 전달되었다면, Sticky Session이 활성화된 경우 클라이언트 A가 보내는 이후의 모든 요청은 세션이 유지되는 동안 EC2 인스턴스 1로만 전달됩니다.

Sticky Session은 다음 AWS ELB 유형에서 지원됩니다:
*   **Classic Load Balancer (CLB)**
*   **Application Load Balancer (ALB)**
*   **Network Load Balancer (NLB)**

### Sticky Session의 동작 원리

Sticky Session은 주로 HTTP/HTTPS 요청에서 **쿠키(Cookie)**를 기반으로 동작합니다.

1.  **초기 요청:** 클라이언트가 로드 밸런서에 첫 요청을 보냅니다.
2.  **인스턴스 할당:** 로드 밸런서는 요청을 처리할 백엔드 인스턴스를 선택하고, 해당 인스턴스에 요청을 전달합니다.
3.  **쿠키 발행:** 로드 밸런서(또는 애플리케이션)는 특정 백엔드 인스턴스 ID 또는 관련 정보를 담은 쿠키를 생성하여 클라이언트에게 응답과 함께 전송합니다. 이 쿠키에는 만료 기한이 설정됩니다.
4.  **후속 요청:** 클라이언트는 이후의 모든 요청에 이 쿠키를 함께 포함하여 로드 밸런서에 보냅니다.
5.  **세션 유지:** 로드 밸런서는 이 쿠키를 확인하여 이전에 할당되었던 동일한 백엔드 인스턴스로 요청을 라우팅합니다.
6.  **쿠키 만료:** 쿠키의 만료 기한이 지나면, 클라이언트는 새로운 백엔드 인스턴스로 라우팅될 수 있습니다.

#### 주요 사용 사례

Sticky Session의 가장 큰 이점은 **사용자 세션 데이터의 무결성 유지**입니다.
*   **로그인 정보:** 사용자가 로그인한 상태를 유지합니다.
*   **장바구니:** 온라인 쇼핑몰에서 사용자의 장바구니 내용을 특정 서버에 저장할 경우 유용합니다.
*   **개인화된 데이터:** 사용자별로 맞춤 설정된 데이터를 특정 서버에서 관리할 때 활용됩니다.

#### 주의할 점: 부하 불균형 (Load Imbalance)

Sticky Session은 사용자 경험을 향상시키지만, **로드 밸런싱의 균형을 해칠 수 있다**는 단점이 있습니다.
특정 클라이언트가 매우 활발하게 요청을 보내는 'Sticky User'인 경우, 해당 사용자가 고정된 백엔드 인스턴스에만 트래픽을 집중시켜 다른 인스턴스에 비해 과부하가 발생할 수 있습니다. 이는 전반적인 시스템 성능 저하로 이어질 수 있으므로, Sticky Session 적용 시에는 이 점을 충분히 고려해야 합니다.

### 두 가지 유형의 Sticky Session 쿠키

AWS ELB에서 Sticky Session을 설정할 때 사용할 수 있는 쿠키에는 크게 두 가지 유형이 있습니다.

#### 1. 애플리케이션 기반 쿠키 (Application-Based Cookie)

이 유형의 쿠키는 애플리케이션 자체에서 생성하고 관리합니다.

*   **어플리케이션이 직접 생성:** 백엔드 애플리케이션이 고유한 세션 ID를 담은 사용자 정의 쿠키를 생성하여 응답 헤더에 포함시킵니다. 이 쿠키에는 애플리케이션이 필요로 하는 모든 사용자 정의 속성을 포함할 수 있습니다. 로드 밸런서는 이 쿠키의 이름만 알면 됩니다.
    *   **예시:** `MYCUSTOMSESSIONID`
    *   **주의:** 다음 이름들은 AWS ELB에서 내부적으로 사용하므로, 애플리케이션 기반 쿠키 이름으로 사용해서는 안 됩니다.
        ```
        AWSALB
        AWSALBAPP
        AWSALBTG
        ```
*   **ELB가 생성:** 로드 밸런서가 애플리케이션을 대신하여 쿠키를 생성합니다. 이때 ELB는 `AWSALBAPP`라는 이름의 쿠키를 사용합니다. 이 쿠키는 애플리케이션에서 설정한 세션 유지 정보를 기반으로 합니다.

#### 2. 지속 시간 기반 쿠키 (Duration-Based Cookie)

이 유형의 쿠키는 로드 밸런서가 직접 생성하고 관리하며, 특정 만료 시간을 가집니다.

*   **ELB가 생성:** 로드 밸런서가 `AWSALB` (ALB용) 또는 `AWSELB` (CLB용)라는 이름의 쿠키를 생성합니다.
*   **특정 지속 시간 설정:** 이 쿠키는 로드 밸런서 설정에 따라 1초에서 7일까지의 만료 기간을 가집니다. 만료 기간이 지나면 클라이언트는 다른 인스턴스로 라우팅될 수 있습니다.

### AWS ELB에서 Sticky Session 설정하기

AWS 콘솔에서 Application Load Balancer(ALB)의 Sticky Session을 설정하는 방법은 다음과 같습니다.

1.  **Target Group 선택:** AWS EC2 콘솔에서 'Load Balancers' 아래의 'Target Groups' 메뉴로 이동하여 Sticky Session을 적용할 대상 그룹을 선택합니다.
2.  **속성 편집:** 선택한 대상 그룹의 'Actions' 드롭다운 메뉴에서 'Edit attributes'를 클릭합니다.
3.  **Stickiness 활성화:** 'Attributes' 페이지에서 스크롤을 내려 'Stickiness' 섹션을 찾습니다. 'Stickiness' 체크박스를 선택하여 활성화합니다.
4.  **쿠키 유형 선택 및 설정:**
    *   **Load balancer generated cookie (지속 시간 기반):**
        *   로드 밸런서가 쿠키를 생성하며, 'Duration' 필드에서 1초에서 7일까지의 만료 기간을 설정할 수 있습니다. (기본값은 1일)
    *   **Application-based cookie (애플리케이션 기반):**
        *   애플리케이션이 생성한 쿠키를 사용하며, 'App cookie name' 필드에 애플리케이션에서 사용하는 쿠키 이름을 입력해야 합니다.
5.  **변경 사항 저장:** 설정을 완료한 후 'Save changes' 버튼을 클릭합니다.

### Sticky Session 동작 확인하기

Sticky Session이 제대로 작동하는지 확인하는 가장 좋은 방법은 브라우저의 개발자 도구를 활용하는 것입니다.

1.  **개발자 도구 열기:** 웹 브라우저에서 `F12` 키를 누르거나, '개발자 도구'를 엽니다.
2.  **네트워크 탭 이동:** 개발자 도구 창에서 'Network' 탭을 선택합니다.
3.  **페이지 새로고침:** 웹 페이지를 새로고침(F5)합니다.
4.  **요청 및 응답 확인:** 네트워크 탭에 표시되는 요청 중 첫 번째 문서를 클릭합니다.
    *   **응답 헤더 (Response Headers) 확인:** 'Set-Cookie' 헤더를 찾아봅니다. 로드 밸런서가 생성한 `AWSALB` 쿠키 또는 애플리케이션에서 설정한 쿠키를 확인할 수 있습니다. 이 쿠키는 특정 인스턴스에 대한 세션 고정 정보를 포함하며, 만료 기한(`Expires`)도 표시됩니다.
    *   **요청 헤더 (Request Headers) 확인:** 이후 요청에 대한 정보를 클릭하여 'Cookie' 헤더를 확인합니다. 클라이언트가 `AWSALB` 쿠키(또는 애플리케이션 쿠키)를 로드 밸런서로 다시 보내는 것을 볼 수 있습니다.

이러한 쿠키 교환을 통해 로드 밸런서는 동일한 클라이언트의 요청이 항상 동일한 백엔드 인스턴스로 전달되도록 보장하는 것을 확인할 수 있습니다.

## 결론: Sticky Session, 신중한 선택과 최적화

Sticky Session은 분산된 백엔드 시스템 환경에서 사용자 세션의 연속성을 보장하여 매끄러운 사용자 경험을 제공하는 강력한 기능입니다. 로그인 상태 유지, 장바구니 내용 보존 등 세션 데이터가 중요한 애플리케이션에서 특히 유용합니다.

그러나 이 기능은 로드 밸런서의 핵심 목적인 '부하 분산'과 상충될 수 있다는 점을 항상 염두에 두어야 합니다. 특정 인스턴스에 트래픽이 집중되어 부하 불균형을 초래할 경우, 전체 시스템의 성능과 안정성에 부정적인 영향을 미칠 수 있습니다.

따라서 Sticky Session을 적용할 때는 애플리케이션의 특성과 사용자 트래픽 패턴을 면밀히 분석하고, 성능과 안정성 사이의 균형을 찾는 것이 중요합니다. 경우에 따라서는 세션 데이터를 외부에 저장하는 Redis(ElastiCache)와 같은 중앙 집중식 세션 저장소를 활용하여 백엔드 인스턴스를 스테이트리스(Stateless)하게 유지하는 것이 더 확장성 있고 효율적인 해결책이 될 수 있습니다. Sticky Session은 세션 관리 전략의 한 가지 유용한 도구이며, 적절한 상황에 신중하게 적용될 때 그 가치를 발휘합니다.
