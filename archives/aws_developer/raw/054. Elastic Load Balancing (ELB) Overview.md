# 054. 💡 AWS Elastic Load Balancer: 트래픽 분산과 고가용성의 핵심

AWS Elastic Load Balancer(ELB)는 여러 EC2 인스턴스에 걸쳐 애플리케이션 트래픽을 효율적으로 분산하여 고가용성과 확장성을 제공하는 핵심 서비스입니다.
ELB는 사용자에게 단일 액세스 포인트를 제공하며, 헬스 체크를 통해 비정상 인스턴스를 자동으로 제외하여 안정적인 서비스 운영을 지원합니다.
CLB, ALB, NLB, GWLB 등 다양한 종류의 로드 밸런서를 통해 특정 워크로드에 최적화된 트래픽 관리가 가능하며, 보안 그룹 연동으로 보안을 강화할 수 있습니다.

## 서론

현대 웹 애플리케이션은 끊임없이 변화하는 사용자 트래픽과 서비스 안정성에 대한 높은 기대를 충족해야 합니다. 단일 서버에서 모든 요청을 처리하는 방식은 트래픽 급증 시 성능 저하 및 장애 발생으로 이어질 수 있습니다. 이러한 문제를 해결하고 애플리케이션의 고가용성 및 확장성을 확보하기 위해 '로드 밸런싱(Load Balancing)' 기술이 필수적입니다. AWS Elastic Load Balancer(ELB)는 이러한 요구사항을 충족시키기 위한 AWS의 완전 관리형 서비스로, 개발자들이 안정적이고 효율적인 아키텍처를 구축할 수 있도록 돕습니다.

## 본론

### 로드 밸런서란 무엇인가요?

로드 밸런서는 서버 또는 서버 세트로, 수신된 트래픽을 여러 백엔드 또는 다운스트림 EC2 인스턴스(서버)로 전달하는 역할을 합니다. 즉, 외부로부터 들어오는 수많은 요청을 여러 대의 서버에 균등하게 나누어 처리함으로써 특정 서버에 부하가 집중되는 것을 방지합니다.

**작동 원리:**
예를 들어, 세 대의 EC2 인스턴스가 있고 이들 앞에 Elastic Load Balancer가 위치한다고 가정해 봅시다. 세 명의 사용자가 Elastic Load Balancer에 직접 연결하면, 로드 밸런서는 첫 번째 사용자 요청을 첫 번째 EC2 인스턴스로, 두 번째 요청은 두 번째 인스턴스로, 세 번째 요청은 세 번째 인스턴스로 분산합니다. 이러한 방식으로 더 많은 사용자가 연결될수록 트래픽은 EC2 인스턴스 전반에 걸쳐 균등하게 분산됩니다. 사용자는 어떤 백엔드 인스턴스에 연결되는지 알지 못하며, Elastic Load Balancer라는 단일 엔드포인트에만 연결하면 됩니다.

### 로드 밸런싱의 핵심 이점

로드 밸런서를 사용해야 하는 이유는 다음과 같습니다.

*   **트래픽 분산:** 여러 다운스트림 인스턴스에 부하를 분산하여 개별 인스턴스의 과부하를 방지합니다.
*   **단일 액세스 지점 노출:** 애플리케이션에 대한 단일 액세스 지점(DNS 이름)을 제공하여 사용자가 복잡한 백엔드 구조를 알 필요 없게 합니다.
*   **장애 처리:** 다운스트림 인스턴스의 장애를 자동으로 감지하고, 비정상 인스턴스로 트래픽 전송을 중단하여 애플리케이션의 연속성을 보장합니다.
*   **상태 확인(Health Checks):** 인스턴스의 상태를 지속적으로 확인하여 트래픽을 보낼 수 있는 건강한 인스턴스만 식별합니다.
*   **SSL/TLS 종료:** HTTPS 암호화 트래픽을 로드 밸런서에서 종료하여 백엔드 인스턴스의 부하를 줄이고 보안을 강화할 수 있습니다.
*   **세션 고정(Stickiness):** 특정 사용자의 요청을 항상 동일한 백엔드 인스턴스로 보내야 하는 경우(예: 세션 정보 유지), 쿠키를 사용하여 세션을 고정할 수 있습니다.
*   **고가용성:** 여러 가용 영역(Availability Zone)에 걸쳐 인스턴스를 배포하고 로드 밸런싱하여 높은 가용성을 제공합니다.
*   **트래픽 분리:** 클라우드에서 퍼블릭 트래픽과 프라이빗 트래픽을 분리하여 관리할 수 있습니다.

### AWS Elastic Load Balancer (ELB)의 특징

AWS Elastic Load Balancer는 AWS에서 완전 관리형으로 제공되는 로드 밸런서입니다. 이는 AWS가 로드 밸런서의 업그레이드, 유지보수, 고가용성을 직접 관리한다는 것을 의미합니다.

*   **관리형 서비스:** AWS가 로드 밸런서의 모든 운영 측면을 책임지므로, 사용자는 인프라 관리에 대한 부담 없이 애플리케이션 개발에 집중할 수 있습니다.
*   **비용 효율성 및 운영 편의성:** 자체 로드 밸런서를 설정하고 관리하는 것보다 훨씬 비용 효율적이며, 확장성 측면에서도 AWS ELB를 사용하는 것이 합리적입니다.
*   **다양한 AWS 서비스와의 통합:** ELB는 EC2 인스턴스뿐만 아니라 Auto Scaling 그룹, Amazon ECS, AWS Certificate Manager(ACM), Amazon CloudWatch, Amazon Route 53, AWS WAF, AWS Global Accelerator 등 수많은 AWS 서비스와 긴밀하게 통합되어 강력한 솔루션을 제공합니다.

### Health Checks: 애플리케이션 상태 모니터링

헬스 체크는 Elastic Load Balancer가 EC2 인스턴스가 제대로 작동하는지 확인하는 핵심 메커니즘입니다. 만약 인스턴스가 제대로 작동하지 않는다면, 로드 밸런서는 해당 인스턴스로 트래픽을 보내지 않아야 합니다.

**헬스 체크 작동 방식:**
로드 밸런서는 지정된 프로토콜, 포트, 경로(엔드포인트)를 사용하여 인스턴스의 상태를 확인합니다. 예를 들어, `HTTP` 프로토콜의 `4567` 포트에 `/health` 엔드포인트로 요청을 보낼 수 있습니다. 이 경로가 애플리케이션의 상태를 확인하는 엔드포인트일 수 있습니다. EC2 인스턴스가 HTTP 200 상태 코드를 포함한 "OK" 응답으로 응답하지 않으면, 해당 인스턴스는 '비정상(unhealthy)'으로 표시되며 Elastic Load Balancer는 해당 인스턴스로 트래픽을 보내지 않습니다.

### AWS ELB의 다양한 종류

AWS는 4가지 종류의 관리형 로드 밸런서를 제공하며, 각각 다른 계층에서 작동하며 특정 사용 사례에 최적화되어 있습니다.

| 로드 밸런서 종류      | 출시 년도 | 작동 계층 | 지원 프로토콜                      | 특징 및 용도                                     |
| :-------------------- | :-------- | :-------- | :--------------------------------- | :----------------------------------------------- |
| Classic Load Balancer (CLB) | 2009      | L4/L7     | HTTP, HTTPS, TCP, SSL/Secure TCP | 구식(Deprecated). 새로운 사용에는 권장되지 않음. |
| Application Load Balancer (ALB) | 2016      | L7 (애플리케이션) | HTTP, HTTPS, WebSockets            | HTTP/S 트래픽, 마이크로서비스, 컨테이너 기반 앱, 경로/호스트 기반 라우팅, 복잡한 라우팅 규칙 |
| Network Load Balancer (NLB) | 2017      | L4 (네트워크) | TCP, TLS, Secure TCP, UDP          | 극히 낮은 지연 시간, 고성능, 정적 IP 주소 필요, 대량의 TCP/UDP 트래픽                                   |
| Gateway Load Balancer (GWLB) | 2020      | L3 (네트워크) | IP 프로토콜                        | 가상 어플라이언스(방화벽, 침입 방지 시스템 등) 체이닝 및 투명한 네트워크 게이트웨이 역할 |

**내부(Internal) 및 외부(External) 로드 밸런서:**
로드 밸런서는 네트워크 구성에 따라 내부(프라이빗 액세스) 또는 외부(퍼블릭 액세스)로 설정할 수 있습니다. 웹사이트와 같은 공용 애플리케이션에는 외부 로드 밸런서가, 내부 서비스에는 내부 로드 밸런서가 사용됩니다.

### 로드 밸런서와 보안 그룹 구성

로드 밸런서 환경에서 보안은 매우 중요합니다. 사용자 트래픽 흐름에 맞춰 로드 밸런서와 백엔드 EC2 인스턴스의 보안 그룹을 적절히 설정해야 합니다.

#### 1. 로드 밸런서 보안 그룹

사용자는 HTTP(80 포트) 또는 HTTPS(443 포트)를 사용하여 로드 밸런서에 접속합니다. 따라서 로드 밸런서의 보안 그룹은 모든 IP 주소(`0.0.0.0/0`)로부터 이러한 포트에 대한 인바운드 트래픽을 허용해야 합니다.

```yaml
# 로드 밸런서 보안 그룹 인바운드 규칙 예시
- Protocol: TCP
  Port Range: 80
  Source: 0.0.0.0/0
  Description: HTTP 트래픽 허용 (전 세계)

- Protocol: TCP
  Port Range: 443
  Source: 0.0.0.0/0
  Description: HTTPS 트래픽 허용 (전 세계)
```

#### 2. EC2 인스턴스 보안 그룹

EC2 인스턴스는 오직 로드 밸런서로부터 오는 트래픽만 허용해야 합니다. 이는 외부에서 EC2 인스턴스로 직접 접근하는 것을 막아 보안을 강화하는 중요한 메커니즘입니다. EC2 인스턴스의 보안 그룹 인바운드 규칙의 소스(Source)를 IP 범위 대신 로드 밸런서의 보안 그룹 ID로 지정합니다.

```yaml
# EC2 인스턴스 보안 그룹 인바운드 규칙 예시
- Protocol: TCP
  Port Range: 80 # 또는 애플리케이션이 사용하는 포트
  Source: sg-xxxxxxxxxxxxxxxxx # 로드 밸런서의 보안 그룹 ID
  Description: 로드 밸런서에서 오는 HTTP 트래픽만 허용
```
이 설정을 통해 EC2 인스턴스는 로드 밸런서로부터 시작된 트래픽만을 허용하게 되어, 전체 아키텍처의 보안을 크게 향상시킬 수 있습니다.

## 결론

AWS Elastic Load Balancer는 클라우드 기반 애플리케이션의 안정성, 확장성, 그리고 효율성을 보장하는 핵심 서비스입니다. 트래픽 분산, 장애 처리, 상태 확인, SSL/TLS 종료, 그리고 다양한 AWS 서비스와의 통합을 통해 개발자는 복잡한 인프라 관리 부담 없이 고성능의 애플리케이션을 구축하고 운영할 수 있습니다. Classic Load Balancer부터 최신 Gateway Load Balancer까지, 다양한 요구사항에 맞는 ELB를 선택하여 최적의 아키텍처를 구성하는 것이 중요합니다. 로드 밸런서와 백엔드 인스턴스의 보안 그룹을 올바르게 구성하여 트래픽 흐름의 보안을 강화하는 것 또한 잊지 말아야 할 중요한 고려 사항입니다.
